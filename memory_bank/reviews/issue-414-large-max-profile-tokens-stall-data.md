## Findings

### F1 (Low) - The comment claims the private attribute is left out of equality, but in pydantic 2.12.4 it is not
`src/prme/models/profile.py:84-87` says the request hash "is left out of the model's dump and equality." Dump is correct, equality is not: pydantic 2.12.4 `BaseModel.__eq__` compares `__pydantic_private__` before the field comparison (`site-packages/pydantic/main.py:1156-1161`). Two field-identical `ProfilePublication` values therefore compare unequal when only one has had `request_hash` read (verified directly against 2.12.4). No durable path depends on `ProfilePublication` equality today: replay and retry use `checksum` (`src/prme/storage/profile_publication.py:38-47`; `src/prme/storage/profile_work.py:419-442`), and no `src/` or `tests/` site compares two plans. So this is a comment/latent-risk defect, not a data change. Either correct the comment or keep any future plan comparison on `checksum`.

### F2 (Low) - The stated staleness guard is incomplete: the nested nodes are mutable
The comment justifies the cache with "the fields it reads are frozen" (`src/prme/models/profile.py:84-86`). `ProfilePublication` is frozen, but its `node`, `sources` and `previous` are `MemoryNode` values and `MemoryObject` is `frozen=False` (`src/prme/models/base.py:21`), so those nested objects can be edited in place. `profile_request_hash` reads them (`src/prme/models/profile.py:41-56` via the property at `:119-128`). The actual guard is the JSON round-trip snapshot at each boundary (F5 list above), which `src/prme/models/derivation.py:4` already relies on ("Mutable nested node models must be snapshotted before storage I/O"). Today nothing edits a plan's nested nodes after the first hash read, and each boundary uses its own copy, so no stale value is reachable. This becomes a real staleness bug the moment some caller does `plan.node.<attr> = ...` (or a `model_copy(update=...)`) after `request_hash` was read, because the old code recomputed and the new code would not. Worth a short comment saying the guarantee is the snapshot copy, not field immutability.

### F3 (Follow-up, pre-existing) - PostgreSQL prepare/commit still serialize the full profile on the event loop
The change moves only the initial copy worker-side in `commit_postgres` (`src/prme/storage/profile_publication.py:206-211`). Several full-profile deserializations/checksums still run on the loop in the PostgreSQL path, so the "no stall" criterion is demonstrated for the tested DuckDB path but not for PostgreSQL:
- `_replayed` on the replay branch: `model_validate_json` plus two `checksum` calls (`:228`, body `:38-47`).
- `validate_pg_work` on every managed commit: `unpack(saved)` re-validates and checksums the stored prepared plan (`src/prme/storage/profile_work.py:476-494`, `:419-442`, `:59-66`).
- `_validate(plan, current, prior_ids)`: `node_checksum` over every source and previous node (`src/prme/storage/profile_publication.py:250`, `:50-58`).
- `_payload(plan)`: `plan.checksum` plus `plan.model_dump_json()` (`:281`, `:31-35`).
- `_prepare_pg` likewise: `unpack(prior)`/`unpack(value)` and `payload(plan)` on the loop (`src/prme/storage/profile_work.py:268`, `:297`, `:315`).

This is not a regression introduced by this change (those calls were already on the loop); it means the issue's "no stall for a very large `max_profile_tokens`" is not fully closed for Postgres-backed deployments. Flagging for the parent to decide scope; it does not touch durable bytes.

### F4 (Follow-up, pre-existing) - Profile collection/discard still validates and checksums full profiles on the loop
`collect_profile_staging`/`discard_profile` paths still deserialize/checksum on the event loop: `ProfileCollectionFence.__init__` (`src/prme/storage/profile_collection.py:67`), `acknowledge` (`:102`, `:123`), and both `delete_profile_stage` copies (`src/prme/storage/lexical_index.py:741`, `src/prme/storage/vector_index.py:593`). These are separate operator operations, not the build/publication path, so this is out of the ticket's build scope and is not a regression; recorded so the residual stall is not mistaken for fixed.

### F5 (Note) - The DuckDB connection lock is now held during the validation copy
`commit_duckdb` acquires the shared `store._conn_lock` at `src/prme/storage/profile_publication.py:87` and now keeps it for the duration of `copy_plan` inside `_commit_duckdb` (`:100`). The event loop itself stays free because the copy runs via `run_to_completion`/`asyncio.to_thread`, so this is not an issue-#414 stall. It does extend the exclusive window shared with every other operation on that connection by the validation time of a store-sized profile; concurrent coroutines wait on the lock rather than blocking the loop, and no deadlock is possible because the copy takes no lock and does not need the loop. Worth measuring on a large store, not a correctness issue.

### F6 (Note) - Vector stage validates against provider/index values read outside the write lock
`VectorIndex.stage`'s `prepared` reads `self._provider.model_*` and `self._index.ndim` on a worker (`src/prme/storage/vector_index.py:481-484`) before `_write_lock`/`_conn_lock` are taken at `:491-492`, so the check-to-write window now includes an await; previously the check and the lock acquisition were in one synchronous block. `_do_clear` can reassign `self._index` under the locks (`:890`), but the dimension and provider identity are stable, and the staged vector is derived from the validated copy, so the written row is unchanged. Low risk; the durable staging bytes are not affected.
