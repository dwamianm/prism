## Verdict

The implementation is sound on its main path and matches the #517 deduplicate contract. No crash or wrong-cursor bug found. Four things need attention before this is a clean deliverable: the RFC/CHANGELOG completeness wording overstates what the vector top-k search guarantees, the `content_equals_any` empty-list contract differs between the SQL backends and the admitted view, and the acceptance-#3 test evidence does not actually isolate the incremental name-lookup path. Details below.

## Checklist results

### Agent 1 (correctness)

- **Write-determined candidate set: holds for the string rules, overstated for the semantic rule.** See F1. Entity `content` is not in `_UPDATE_ALLOWED_FIELDS` on either backend (`duckpgq_graph.py:1183-1199`, `pg/graph_store.py:679-695`), every node-state write bumps `updated_at` (`duckpgq_graph.py:1221-1224`, `lifecycle.py:157,213`, `condition_evaluation.py:408-410`, `reinforcement.py:182,258`), and `compatible_provenance` only depends on node fields. The lookup is then re-filtered with the exact same predicates and confidences through `_string_alias_candidate` (`alias_resolution.py:164-172`, 0.95/0.90) and the same `compatible_admitted_pair(alias_pair_allowed, ...)` check (`alias_resolution.py:395`, `:402`). ## Findings

### F1 - Should Fix: "provably write-determined" wording is stronger than the semantic search guarantees
`src/prme/organizer/alias_resolution.py:190-195` searches `k=10`; `docs/RFC-0015-Self-Organizing-Memory.md:503-506` says the candidate set is fully write-determined and "the name lookup and the vector search supply the other endpoint"; `docs/RFC-0015-Self-Organizing-Memory.md:484` says "a semantic twin that is not on the page is still found"; `src/prme/organizer/jobs.py:748-753`, `src/prme/organizer/watermarks.py:28-31` and `CHANGELOG.md:15` repeat the claim. Counterexample: a new entity B is semantically similar to unchanged A (score >= 0.85) but B has ten more-similar neighbours so A is not in B's top-10; A is outside the window, so A's own search is not run this cycle and the pair is never found, while the full scan (which searches every page entity) does find it from A's side. The *eligibility* argument (an endpoint must be written) is correct; the *discovery completeness* claim is not. This is the same top-k bound `deduplicate` has, so recommend qualifying the RFC sentence and the job docstring exactly as the protected-store limitation is qualified (`docs/RFC-0015-Self-Organizing-Memory.md:519-522`), rather than changing the algorithm. Impact is a rare missed semantic link; no test covers it (see F4).

### F2 - Should Fix: `content_equals_any=[]` behaves differently in the admitted view and in SQL
`src/prme/privacy/read_graph.py:128-131` builds `equals_set = set()` for an empty list, and `:154-155` then rejects every node. `src/prme/storage/duckpgq_graph.py:1381` and `src/prme/storage/pg/graph_store.py:428` both guard with `and content_equals_any`, so an empty list is a no-op and returns every node. The new public docstring `src/prme/storage/graph_store.py:230-232` ("equals ANY of the given strings") reads as match-nothing, which the SQL backends violate. Not reachable from `_alias_name_forms` (always non-empty), but `content_equals_any` is now a public `GraphStore.query_nodes` argument. Cheapest fix: make the view use `None if not content_equals_any else {...}`, or document "empty list = no filter" and align the view.

### F3 - Should Fix: the incremental-vs-full alias test is masked by the 60-second watermark overlap
`tests/test_organizer_incremental.py:591-597` stores the second batch immediately after the first run; `_run_incremental` records `completed_through = ceiling - 60s` (`jobs.py:121-126`, `jobs.py:61`), so the second run's lower bound is still before the first batch's `updated_at` and the "incremental" run re-scans every node, including `JavaScript` and `alpha`. The test therefore exercises the overlap, not the name-lookup path that is supposed to find a twin outside the window. Suggested: in the test set `jobs_module._WATERMARK_OVERLAP = timedelta(0)` (or set an older watermark) before the second batch, and assert that the unchanged twin is still merged; that is the only evidence for the novel mechanism.

### F4 - Should Fix: coverage gaps for the core mechanisms
Missing tests, all on DuckDB unless noted:
- Cross-page name twin: `tests/test_organizer_incremental.py:371` stores each pair contiguously so the twin is always on the same page; a case like `[JavaScript, alpha, js]` with page size 2 is untested.
- Cross-window name twin: masked by F3.
- Semantic-alias incremental path: `_semantic_alias_candidates` is only exercised in incremental mode indirectly; no test creates two differently named entities above `alias_similarity_threshold` (0.85, `src/prme/config.py:678-683`) and asserts the incremental run finds a twin not in the page (this is also what would have exposed F1).
- Failure/retry parity: dedupe has `tests/test_organizer_incremental.py:468` (failed page does not move the cursor) and `:533` (failed neighbour search reported and retried); alias has neither, although `jobs.py:885-902` implements both branches.
- Semantic link idempotency (second run creates no second RELATES_TO) is untested for alias, though `propose_alias` is idempotent (`alias_proposal.py:271-274`).
- On PostgreSQL: no budget-stop/resume or failure test for alias (`tests/test_organizer_incremental_pg.py:175` is convergence only).

### F5 - Consider: case/whitespace semantics differ between the admitted view and SQL
`src/prme/privacy/read_graph.py:130,154` normalizes with `strip().casefold()`; the SQL backends use `LOWER(TRIM(content))` (`duckpgq_graph.py:1384-1386`, `pg/graph_store.py:429-430`). `casefold` and `lower` diverge on non-ASCII (e.g. `ß`/`ss`), `TRIM` removes spaces only while `strip()` removes all whitespace, and the view filters projected content while SQL filters stored content. For the alias job the extra view permissiveness is harmless (`_string_alias_candidate` re-checks with `lower`), but it is a real behavioural difference in a new public filter, and it follows the existing `content_contains_any` pattern (`read_graph.py:150-151`) rather than fixing it.

### F6 - Consider: per-entity name lookups make the protected-store cost O(changed x scope)
`src/prme/privacy/read_graph.py:133-158` implements `content_equals_any` by paging the whole admitted scope through `_all_nodes` and filtering in Python, with no SQL LIMIT pushdown. `_find_aliases_in_page` calls it once per changed entity (`alias_resolution.py:376-383`), so on a privacy-admitted store an incremental alias page now costs `changed * scope` plus the existing `scan_changed_nodes` cost. The RFC "Known limitation" (`docs/RFC-0015-Self-Organizing-Memory.md:519-522`) names only `scan_changed_nodes`; the name lookup should be added to it (or pushed into `scan_nodes`, which already accepts `content_contains_any`).

### F7 - Consider: `seen_pairs` is shared across pages (deviation from deduplicate)
`src/prme/organizer/jobs.py:834,875` passes one `seen_pairs` for the whole run; `src/prme/organizer/deduplication.py:164` rebuilds it per page. Sharing is justified and safe here (it prevents re-proposing a pair resolved on an earlier page and is not needed for correctness because revalidation would reject a retired pair anyway), but it is a divergence from the analogue and should be noted in the handler docstring if kept.

### F8 - Consider: the 500-row name-lookup bound is a real completeness bound
`src/prme/organizer/alias_resolution.py:307-309` and `:382` cap the lookup at the 500 newest matching entities (`ORDER BY created_at DESC`, `duckpq_graph.py:1400-1404`). An older twin beyond that is not found even though it is in the store. The comment calls it "a page bound, not a completeness claim", which is honest, but `CHANGELOG.md:15` and `docs/RFC-0015-Self-Organizing-Memory.md:484` still say an unchanged twin "is still found" without the bound. It is no worse than the full scan's 100-entity page (`deduplication.py:96-98`), so this is documentation precision only.

### F9 - Consider: canonical tie-break depends on candidate order (shared with deduplicate)
`src/prme/organizer/alias_resolution.py:575-578` prefers the earlier argument when `created_at` is exactly equal and length/confidence/evidence all tie. In the full scan the earlier argument is determined by `query_nodes` order; in the incremental path it is the changed entity. If two case-variant entities share an identical `created_at`, the surviving content can differ between the two paths, which would break the "same store" property. Very low probability (needs identical microsecond timestamps) and identical to `_pick_canonical` (`deduplication.py:283-286`), so it is a shared pre-existing edge case, not a regression.

### Nit
`tests/test_organizer_incremental.py:1-12` still says "the converted job" (singular) and "Three properties are checked on the converted job"; the file now covers two jobs.
